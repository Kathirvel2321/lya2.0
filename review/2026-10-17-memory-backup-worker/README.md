## Implemented

New [memory_b2_backup.py](../../brain/memory_b2_backup.py) adds `backup_once()` with explicit synthetic/approval flags. No production caller or background timer is installed. A trusted caller supplies a preverified pack, exact `RecoveryPins`, a fresh observation callback, service credential, lab bucket/prefix and a new receipt path. No unlock key is accepted or read. This worker checks ciphertext fingerprints; the existing pack producer/recovery layer remains responsible for authenticated snapshot validity.

The worker bounds all three ciphertext files together to eight MiB before network authorization. It accepts only a disposable `lya-memory-lab/<scope>/` prefix, verifies fresh pins before transfer, requires exactly `listBuckets`, `readFiles` and `writeFiles` on one exact bucket/prefix, and requires the pilot key to expire within one day with at least a minute remaining. It checks that the target is private. Master/unrestricted, delete-capable, wrong-prefix and permanent credentials are refused. These are checks of authenticated provider metadata; actual server-side permission denials still need a live pilot.

Only verified HTTPS is used, with strict vendor host roles for discovered API/download/upload addresses. Python's built-in HTTPS client follows no redirects, uses no browser cookies or environment proxies, and closes every connection. Metadata is bounded to 64 KiB, calls to sixteen and individual I/O waits to four seconds, with cancellation and a cooperative 45-second worker deadline. Header/slow-drip behavior is not a hard process deadline; production execution needs the separately qualified OS supervision/resource profile.

Object names derive from the lineage and complete pin fingerprint. The worker reads all expected names first, uploads only missing ciphertext and refuses divergent existing bytes. Native SHA-1 is used only for B2's upload checksum; exact ciphertext comparison and trusted SHA-256 remain the recovery checks. Uploads request SSE-B2 encryption explicitly. After all uploads, every file is downloaded again and compared, and fresh trust is checked before publishing a content-free new local receipt with the existing atomic-create helper. A provider's upload reply alone is insufficient. The receipt is never used as the next run's source of trust.

Committed-upload reply loss is reconciled by the next worker reading the existing bytes. A known successful sequential retry adds no extra objects/versions. There is no distributed writer lock or atomic create-if-absent guarantee at B2: overlapping/in-flight workers can produce duplicate versions. Run one serialized worker; account-wide quota, version retention/cleanup, uncertain in-flight retry/backoff and scheduling remain deployment work. Per-run byte/request limits are not a zero-spend guarantee or aggregate account cap. The worker never deletes or changes permissions/retention. A compromised write credential can still overshadow/hide names; minimal capabilities are not immutable storage.
