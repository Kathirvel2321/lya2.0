## Publication and recovery

`RecoveryHead` binds the existing complete `RecoveryPins` to the encrypted trust record's exact fingerprint. `SyntheticRecoveryLatest` keeps confirmed/pending heads in a separate caller-trusted SQLite file, following the existing witness's schema-ID checks, existing-file-only opening, synchronous transactions, explicit synthetic opt-in and approval patterns. It stores metadata only; no unlock/storage/recovery key or memory content is saved there. This local lab store is plaintext metadata and is not production protected catalogue storage.

1. Explicit `create()` initializes a **new** trusted store. This is a first-time bootstrap decision, not a recovery fallback. Opening a missing/corrupt store or requesting a missing lineage refuses; the implementation never reconstructs freshness from backup files.
2. `begin(previous, candidate)` durably reserves the exact candidate using compare-and-swap. Checkpoint sequence and writer epoch cannot move backwards; an unchanged sequence cannot change checkpoint or backup bytes. Capsule rotation and divergent same-state re-encryption require other workflows and are refused. A writer-epoch-only advance with identical checkpoint/backup is supported. Competing candidates cannot both reserve the same predecessor.
3. Once pending, `head()` and `restore()` refuse both the old and candidate copies. There is no automatic rollback, abort, recreation or preference for an older available backup.
4. `finish(candidate, pack, trust, unlock)` requires that exact pending candidate, opens the trust record against its reserved fingerprint, requires exact decoded pins, and verifies the entire three-file pack. Only then does one SQLite commit replace the confirmed head and clear pending. Missing/bad inputs, cancellation and failed commits leave uncertainty pending. Exact retries are idempotent, including a committed response lost to process death; a later head prevents stale retries from moving backwards.
5. `restore(lineage, pack, trust, destination, unlock)` obtains the expected fingerprints from the confirmed separate store. The caller cannot supply an old trusted fingerprint to this method. It serializes the observation and existing encrypted/quarantined restore against publication with a SQLite transaction. A failed restore may leave an unpublished/quarantined output under existing restore semantics, never an activation grant or success inferred from file presence.

Call `begin()` before publishing the candidate's pack/trust copies or acknowledging that publication; verify/retry `finish()` afterwards. Candidate pins must already come from a trusted caller. This is a last-confirmed-**publication** protocol, not automatic observation of every source mutation. It is not wired to the existing memory authority acknowledgement path. Source changes acknowledged before this protocol is consulted are not covered by this isolated integration; production cutover requires coordination with that authority/witness, protected catalogue and writer fencing.

## Failure and rollback boundary

The tests preserve a current separate latest-store file while offering older authenticated pack/trust pairs. Recovery refuses those old pairs even when both are rolled back together, and also rejects mixed old/current inputs. A half-copied candidate remains pending across store reopen; the old pack is not silently restored. Publishing the exact verified candidate in a new artifact directory completes the reservation.

Four synchronized child-process exits exercise before/after `begin` and `finish` commits. Before a transaction commits, SQLite preserves the preceding state; after begin commits, restart blocks recovery; after finish commits, restart observes the exact new head. Retrying each interrupted transition reconciles without a second head or backwards publication. Those transaction-only crash cases mock artifact validation; separate end-to-end cases use actual generated encrypted pack/trust files and SQLCipher recovery.

The fresh-process drill deletes the owned original fake store/catalogue/witness. A child opens the surviving separate latest store and obtains current pins/fingerprint there, rather than from a supplied plaintext pin/fingerprint packet. It restores through the actual latest-store gate. The test reuses the existing verifier's record/search/encryption/old-binding assertions; its test adapter routes that verifier's restore call through the new gate. The child gets only a generated fake unlock through stdin, with no storage key or current fingerprint in its initial packet. Correction, forget/expiry suppression, quarantine, old-binding refusal and zero active bindings/jobs are checked.

Separate folders and WSL processes remain on one physical laptop. **The latest store is assumed independently trusted and surviving. Rolling back that store together with all other copies is still undetectable here.** No independent remote witness, hardware monotonic counter, account boundary, physical recovery copy or clean-machine acceptance was deployed. Pending state deliberately blocks availability until the exact candidate can be completed; there is no speculative rollback escape. The local transaction lock and three-second SQLite lock timeout are not a remote fencing protocol or production load budget. Physical power-loss durability, whole-store quotas/encryption, key rotation and complete authority recovery remain open.
