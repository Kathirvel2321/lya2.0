# Native recovery interface evidence

Date: 2026-09-20. Local implementation and isolated tests; enrollment remains
deferred. No production profile/key was read or modified and nothing was uploaded.

## Delivered

- `desktop/recovery.py`: native backup/restore tabs, approved owner-only note
  selection, masked random recovery key, separate-custody acknowledgement and
  key re-entry. Archive preview authenticates contents and reports active/expired
  counts and whether the destination owner profile is empty. Restore requires a
  second explicit confirmation. User filenames/keys never go to the model.
- `storage/recovery.py`: approved label listing, bounded archive read/preview,
  exact archive digest binding after preview, and ciphertext-only file publication.
  Export approval binds the resolved destination. Same-directory temporary writes
  are flushed and published without replacing an existing target (Windows rename;
  POSIX link). Temporary ciphertext is removed on normal failure/cancellation.
- `desktop/experience.py`: `open recovery`, `memory recovery`, `backup notes`,
  `restore notes`; no guest-to-admin escalation. Quit requests cancellation and
  finishes after the worker returns, without blocking Qt.
- `check-storage-recovery.cmd` now includes `test_recovery_ui.py`.
  `.gitignore` excludes `.lya-notes` archives and recovery temporary files.
- Documentation updated in `desktop/README.md`, `LYA_STORAGE_SECURITY_PLAN.md`,
  `LYA_TASK_ROADMAP.md` and `lya-project-brain.md`.

## Checks and results

- `check-storage-recovery.cmd`: 58 checks passed: 12 recovery core, 33 brain,
  3 approval and 10 native UI/file checks.
- `desktop/check_experience.py`: 13 checks passed, including command opening with
  the original guest session and deferred quit during recovery cancellation.
- Total: 71 distinct checks. Follow-up UI checks after visual/privacy corrections
  use the same ten cases rather than increasing this count.
- Full UI drill: select a fake note -> confirm key -> save real temporary archive
  -> change local encryption key/create a fresh fake profile -> authenticate preview
  -> confirm restore -> compare decrypted restored value. No model, camera,
  microphone, real verifier or external service was involved.
- Failure coverage: guest/default-gate denial, wrong key, nonempty destination,
  key confirmation/custody, session expiry and displayed-data clearing, modified
  archive after preview, cancellation/late worker result, disk failure, destination
  race and session expiry just before file publication.

  `restore-synthetic.png`, `locked-screen.png`. No key is generated or shown in
  those screenshots. Visual review fixed white tab backgrounds and stale note-count

The first drill run found a test assertion mismatch between Windows' short temp
path and its canonical path. The application correctly bound the resolved path;
the assertion now compares parsed resolved paths. Tests subsequently passed.

## Limits and next gate

The real app still has a guest session and no connected trusted approval adapter.
Opening the window therefore remains locked, by design. Synthetic tests do not
prove real owner authentication or clean-device recovery. Never enable a fake
verifier or manually grant an admin role to make this screen work.

Key custody remains the owner's separate responsibility. Re-entry/acknowledgement
does not prove the external copy is durable. Clipboard copying is never automatic;
explicitly revealing/copying the key may expose it to the OS or clipboard tools.
Clearing widgets/references is not guaranteed physical RAM erasure.

Cancellation is cooperative and checked at operation boundaries. A committed
file/database change cannot be reversed by a late cancel; the UI does not claim
otherwise. An OS file operation already in progress may delay shutdown. A crash
can leave an encrypted temporary file. Atomic publication prevents partial
archives/overwrites but does not prove power-loss durability on every filesystem.
The one-second session timer runs only while the dialog is open; no idle backup
loop or decorative animation was added. Battery/latency impact is unmeasured.

The key recovery format covers selected notes and their relationships, not files,
credentials, biometric identities, or the original DPAPI key. T10 remains partial.
Next: connect verified owner sessions/approval when the owner requests that setup,
perform the real recovery drill, then consider encrypted remote transport. No
Google Drive connection, automatic backup or cloud sync is enabled.

Rollback: stop invoking the new dialog; do not reset the repository or overwrite
the live store. Existing `.lya-notes` files can still be handled by the tested
recovery core. Preserve both the archive and its separately held key.
