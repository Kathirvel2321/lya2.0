# Admin bootstrap and visual check — 2026-09-25

The registration view now has a one-shot 720 ms left-to-right accent across the crystal when a Windows verification starts. It does not loop at idle, and reduced-motion mode skips it. It is a visual cue, not a claim that a camera or biometric scanner ran. Synthetic previews: `review-synthetic.png` and `scan-synthetic.png` (synthetic name only).

The Windows Hello helper now echoes a fresh per-attempt nonce only after `Verified`. The desktop rejects an old/unbound result, checks the active encrypted admin record, and offers either first-profile creation or sign-in to a previously created **device-only** admin profile. A different/legacy admin profile cannot be downgraded to device-only sign-in. First-profile creation requires an explicit checkbox after a fresh Windows verification. On success it issues a five-minute session to the native brain, greets the owner, and keeps protected actions locked behind the separate phone-approval gate. Face and voice are **not** enrolled or used for authentication. `sign in` / `unlock lya` reopen this screen.

The admin display name, person ID and privacy-safe audit marker are written atomically inside `%LOCALAPPDATA%\LYA\lya.db.enc` (or configured `LYA_DATA_DIR`). New installs place the DPAPI-wrapped Fernet key in `%LOCALAPPDATA%\LYA\master.key.dpapi`; existing `security/.lya_key` vaults stay on their original key to avoid breaking data before a verified recovery copy. No raw face image, voice recording, PIN, or plaintext recovery credential is saved. The review screen states that this is not a backup. The portable recovery helper was updated to find either key location; fake-key recovery checks passed.

Verification: the full offline `check-t04.cmd` gate passed; 37 focused registration/recovery tests and 23 offscreen desktop checks also passed. A local rebuild of `HelloVerifier.exe` succeeded. A live `HelloVerifier.exe check` was blocked by Windows Application Control both inside and outside the sandbox before any PIN prompt. Consequently **no real admin was enrolled, no live sign-in succeeded, and no identity data was captured**. The UI detects a policy-block start error and stays locked. The executable is locally built and unsigned; do not disable Application Control merely to run it. A trusted distribution or reviewed in-process Windows interop path is needed before a real owner test.

Automatic startup face recognition and unknown-person photo capture were not connected. A camera must actually activate to recognize a face even if no preview window is shown; the current local vision models detect presence/objects but do not establish identity or liveness. An unknown-person record needs a separate visible capture and retention policy. There is no general high-security approval screen yet; the registration cue should not be mistaken for that protection.
