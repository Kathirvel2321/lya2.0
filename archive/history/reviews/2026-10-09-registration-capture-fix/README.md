# Registration camera and voice-capture repair — 2026-10-09

The owner reported a lagging enrollment camera and confirmed setup reached voice capture before failing. The earlier implementation did not expose a specific spoken capture error, so **the exact cause of that live failure is unknown**. Development did not open the camera/microphone, inspect recordings, enroll anyone or change the protected runtime store.

## Why registration remained unfinished

Phone registration and secondary recognition profiles are separate commits. The face/voice profile commit is atomic: all three face views and all three consistent voice samples, explicit final save and fresh phone proof are required. If voice acquisition, quality, consistency or expiry fails, neither set of biometric templates is saved. Completing the visible face step alone therefore does not complete profile registration. This rule remains unchanged; the repair does not create profiles from incomplete samples or bypass phone proof.

## Reproduced issues and changes

- **Choppy, enlarged preview:** the worker sent 320×240 images at at most two frames per second, despite a large native face stage. It now sends bounded 640×480 JPEGs at up to 10 FPS. Capture requests 15 camera FPS where supported, and the acquisition/analysis loop has a 100 ms work budget. The actual camera/backend can deliver less. JPEGs remain capped at 100,000 bytes and the bridge validates dimensions and coordinates. The legacy 320×240 format is still accepted. Native rendering uses smooth image scaling; five actual landmark observations remain attached to their source frame. No model, face-match threshold or security authority changed.
- **Import work after microphone acquisition:** WebRTC voice detection was constructed after the first audio read. Initialization now happens before opening the stream, preventing that work from consuming the active input-buffer budget. This is a reproduced ordering defect, not proof that it caused an overflow on the owner's device.
- **Waiting silence diluted the voice-level check:** the old RMS check measured the entire recording, including waiting. A synthetic late-start sample with usable speech could fall below the unchanged 0.002 threshold solely because of the preceding silence. Energy and clipping now use speech-active blocks. Existing speech-duration, finite-value, clipping, normalized-vector and cross-sample consistency checks remain; overflow still rejects the sample. Temporary copies are cleared on success or failure and the stream closes before preprocessing/inference.
- **Specific reasons were hidden:** worker errors now carry a fixed, strictly validated category, never native device error text, paths, recordings or vectors. LYA speaks a reason for microphone failure, overflow, missing/faint/short/clipped speech, inconsistent samples, processing timeout or expired phone proof. Unknown errors remain generic. `fail()` now includes that safe explanation in the spoken prompt instead of leaving it only in hidden UI text. Expiry during profile setup explains the failure while stopping capture; it does not extend the five-minute phone authority.
- Repeated cancellation instructions were removed from each subsequent capture prompt; they are given at the beginning. Guidance still finishes before capture begins. Escape/close still cancels; spoken commands remain paused during local biometric acquisition. This reduces avoidable narration within the existing proof deadline.

Ordinary NVIDIA transcription, Amy output, main interface, person tiers, keys, encryption, phone proof and sensitive-operation approval were not changed. These voice samples are for a local recognition profile, not cloud transcription. No new dependency was installed. The camera still closes between face captures and is off before voice capture; there is no continuous background camera.
